## 两套服务、两套协议（核心架构事实）

- 管理网关 `http://47.120.10.73:12001`：xrpc 信封 `{com,req:{module,method,params}}` 走 `/startlandapi`，管理员 JWT。

## 完整流程（两步）
1. 前端算 SHA256（`X-File-SHA256` 必填，缺失报 `CHECKSUM_REQUIRED`）+ 生成 UUID v4 幂等键 → `POST /api/v1/app-releases`（form: `file`/`platform=android`/`package_type=apk`；headers: `Idempotency-Key`/`X-File-Size`/`X-File-SHA256`/`Authorization?`）→ 返回 `file_id`+技术元信息。
2. `Admin.PublishAppVersion(file_id + latest_version(major.minor.patch) + build_number(uint64→十进制字符串) + minimum_version + update_title/desc + client_request_id(UUID) + expected_release_id(首发留空))` → `AppVersionRelease`。
3. `ListAppVersions(platform, include_disabled)` 列表；`DisableAppVersion(platform, expected_release_id)` 停用。

## 字段约定要点
- `build_number`/`package_size_bytes` 为 uint64 且无 `[jstype=JS_NUMBER]` → 按项目约定走十进制字符串。
- `status`：active / disabled / superseded；`operator_uid`；时间字段带 JS_NUMBER → formatTimestamp 兼容。
- 安装包 `GET /api/v1/app-releases/{file_id}` 为**公开**下载接口（C 端升级用）；`HEAD` 需内部服务凭据（Admin→文件服务服务端取，前端不做）。

## 上传失败根因定位 + Token 自动刷新机制（2026-09-20 下午）
- **根因诊断**：APK 上传 `NETWORK_ERROR` 本质是 **token 校验失败**。实测证据：文件服务 `106.52.77.108:80` POST 不带 token→`401 AUTH_TOKEN_MISSING`(JSON，请求到后端)；带无效 token→`403` openresty HTML(网关前置拦截)。`token.md` 确认文件服务与 admin 网关共用 HS256/`iss=starland`/取 `UserId` 验签；access token **默认有效期仅 1h**，过期即 `AUTH_TOKEN_EXPIRED`。此前前端 `getAccessToken()` 傻瓜式取 localStorage 旧 token，**从不检查过期、从不刷新**，登录超 1h 即无法自愈。
- **后端刷新契约**：`login.proto` 有 `rpc RefreshToken(RefreshTokenRequest{refresh_token}) returns (LoginResponse)`（starland.login.com）；LoginResponse 含新 access/refresh token + 过期时间。前端此前从未调用。
- **已实现的修复（用户选"两步都做"）**：
  1. 自动刷新核心：`src/lib/auth/session.ts` 新增 `getValidAccessToken()`（过期前自动用 refreshToken 换新并 saveSession，带 `inFlightRefresh` 并发锁避免重复刷新；刷新失败清 session 返 null）；用 `setRefreshHandler`（依赖注入，避开与 auth api 的循环依赖）。
  2. `src/features/auth/api/login.ts` 加 `refreshTokenApi()` + `toSession()`。
  3. `src/features/auth/auth-context.tsx` 模块加载时 `setRefreshHandler` 注册真正的刷新实现。
  4. `src/lib/xrpc/transport.ts`：`xrpcCall`(后台受保护) 改用 `await getValidAccessToken()` 自动带有效 token；`xrpcLoginCall`(登录/刷新) 仍用同步 `getAccessToken()` 避免 RefreshToken 请求递归触发刷新。
  5. 诊断可见化：`fileApi.ts` 上传失败时把 `status/url/responseText` **外加 token 的 `UserId` 与过期剩余时长** 打到 toast；`FileUploadError` 增 `tokenUserId/tokenExpireAt` 字段，便于一眼确认"是否过期"。
- **验证**：`tsc --noEmit` 通过(0)；dev server HTTP 200(HMR 已热更)。
- **待用户验证/后端配合**：用真实管理员账号重新登录后再上传，观察 toast 诊断；若刷新后仍 401/403，则指向 token.md §146 的"Login/Gateway/文件服务 key·issuer 必须一致"部署问题（前端改不了），需后端核对密钥。

## 二次实测：后端网关已放开，但 token 仍被拒（2026-09-20 16:36）
- **新证据（curl 实测）**：文件服务对 `/api/v1/app-releases` 已不再是 403 HTML，改为规范 **401 JSON**：无 token→`AUTH_TOKEN_MISSING`、无效 token→`AUTH_TOKEN_INVALID`（均带 `x-request-id`、JSON body）。说明 openresty 网关白名单已开、请求已到文件服务校验层。
- **路由事实**：`/releases/new` 在 `RequireAuth` 之下（App.tsx L22-24）→ 用户能打开上传页即已登录、本地有 session，故 `getValidAccessToken()` 不会返回 null（否则被踢到 /login）。即前端确实发出了 token，仍被 `AUTH_TOKEN_INVALID` 拒绝。
- **根因收敛**：token 本地未过期（否则自动刷新会触发，刷新失败则清 session 跳登录；用户在页上说明未跳）→ 文件服务验签不通过。几乎可锁定为 **token.md §146：Login / Admin Gateway / 文件服务 三者的 JWT 签名 key 或 `iss=starland` 不一致**，表现为"能登录进后台、但上传 401 拒"。这是**后端部署配置问题，前端代码无法修复**。
- **给用户的判定清单**：① 再传一次看 toast 是否显示 `code=AUTH_TOKEN_INVALID · HTTP 401 · Token: UID=…`（确认是 token 拒而非网络）；② 确认 Admin 后台（列用户/列版本）是否用同一登录正常工作——若 Admin 也 401 则 token 整体无效（登录环境问题），若 Admin 正常但上传 401 则坐实 key/issuer 不匹配；③ 让后端核对三套服务的 HS256 secret 与 issuer 必须一致。

## 后端 token 验签修复（2026-09-20 17:35，实测 201 通过）
