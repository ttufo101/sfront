**重要纠错（覆盖上文错误结论）**：上文写的「GetLinks 先裁剪 → 再检查占位符」是**反的**。实测 `RELAY_HOST` / `ANYTLS_PASSWORD` 各出现 6 次且**只存在于 6 个 proxies 条目里**；若先裁剪，全下架时占位符随之消失，现有 `strings.Contains` 检查必 500。正确顺序：**在原始模板上完成占位符校验与替换 → 再按 listed 裁剪 yaml.Node → base64**。`validateProxyConfig` 的 ≥1 anytls 是「保存模板」校验，模板恒 6 条，不受影响。

1. 全下架空态契约（改 proto + 客户端）→ 直接复用 `errors.ServiceUnavailable` 返回 503 `no available proxy outlet`，零协议/客户端改动；客户端仓库不在环境里。
2. starcore `relayAssignmentCacheTTL=15s` 缓存改造 → 不改代码，弹窗写明「改派后等 15s 再下架」。
3. 中转迁移向导 + 事务 + 2 个新 RPC（`ListRelayAssignmentsByNode` / `DecommissionRelayNode`）→ **降级为前置校验 + 提示**。实证 `t_user_relay_assignment` 总数 0、严格(allow_fallback=0) 0 行；`SetNodeListing` 的 relay 分支加一条 `SELECT uid ... WHERE node_id=? AND allow_fallback=0`，非空则返回带 uid 列表的 BadRequest，运维用现有 `UserRelayAssignmentPanel`(/users/relay/:uid) 逐个改派到指定剩余中转后再下架。
4. 统一节点清单跨服务 join 视图 → 推迟（属菜单合并锦上添花，非下架需求）；菜单合并后也只需在「落地出口」tab 显示状态，不用两个页面各加徽标。

**小优化**：`listing_status` 枚举改 `is_listed TINYINT NOT NULL DEFAULT 1`，表只留 4 列（proxy_name PK / port / node_id / is_listed），审计统一写 `t_admin_audit_log`，表内不存操作人。

**精简后改动量**：2 个新 RPC（`ListProxyOutlets`、`SetNodeListing`）+ 2 个网关 method + 1 张 4 列表 + `GetLinks` 一个裁剪纯函数（约 60–80 行，yaml.v3 Node 定点删 proxies 定义与 3 处 group 引用）+ 1 个壳页面 + 1 个 tab + 1 个确认弹窗 + 1 条前置 SQL。营销页 / YAML 前后端校验器 / 客户端协议 / starcore 缓存 / 用户分配页**全不改**。必须保留：菜单合并、出口表、GetLinks 裁剪、relay 前置校验与规范审计、故障不参与过滤。

**考虑过但否决**：把模板改成 `PROXIES_BLOCK`/`PROXY_NAMES` 两段占位符、GetLinks 只做字符串替换（代码更少），但要一次性改模板 + 改前后端校验器 + 管理员编辑体验变差，不推荐。固有复杂度只剩 YAML 裁剪一项（自由文本模板、每个名字出现 4 次、占位符只在 proxies 内）。

**剩余边界**：全下架 503 可能被客户端当网络错误（需确认可接受）；人工改派后 15s 窗口；换落地机需人工同步中转 mihomo + node_id；已下发客户端需重新拉 GetLinks；`UpdateDataPlaneNode` 老入口无幂等/原因的问题仍在但下架不复用它。

**用户确认（同日）**：中转下架遇强制指定用户时，采用「提示运维先迁移、迁移完才允许下架」的**硬门禁**（不是仅软提示），与上述精简第 3 项一致。落地形态：`SetNodeListing` relay 分支加 `SELECT uid FROM t_user_relay_assignment WHERE node_id=? AND allow_fallback=0`，非空返回带 uid 列表的 BadRequest；运维用现有 `/users/relay/:uid` 页面逐个改派后再点下架。只拦 `allow_fallback=0` 的严格用户（非严格用户会自动回退到健康候选，不受影响）。此门禁把「事务 + 向导」变成「两人工步骤 + 一道校验」，同时让 15s 缓存窗口被人工间隔覆盖。

## 只读排障：SG/NL/FR 三出口测延迟恒超时（用户只要求分析+核对，未改任何代码/数据）

**结论：不是客户端配置、也不是「删除」动作本身导致，而是中转→落地链路断 + 控制面与数据面脱节。**

实证（develop-hy Mihomo external-controller `127.0.0.1:29090/proxies/hy2-landing-<port>/delay`，测速 URL 换 gstatic / cloudflare 两种均一致）：
- 26019 / 26023 / 26024 → `Timeout`；26020 / 26021 / 26022 → 1380 / 596 / 887 ms。与用户看到的三个超时完全对应。
- 两台中转（47.120.10.73 / 106.52.77.108）6 个 anytls listener 26019–26024 **全部在听**，落地映射完全一致 → 无论用户被分配到哪台中转都稳定复现「每次都超时」。
- 真实路由（`/opt/mihomo/conf/config.yaml` 的 `IN-NAME` + hy2 outbound）：26019→139.180.130.194、26020→45.32.20.165、26021/26022→47.251.121.91、26023→78.141.208.60、26024→139.180.130.194。
- 两个坏落地：78.141.208.60 ping 100% 丢包 / SSH22 超时（机器不可达）；139.180.130.194 主机在线、22 开，但 host key 与 known_hosts 不符（重装过）、UDP 业务不通。二者在 `t_node_asset` 里 auth_status=pending/failed、`last_probe_at` 分别为 NULL / 11-13 21:30，**从未纳管成功**，且已于 12:19:14 / 12:19:31 软删。

**「落地机删了是否导致超时」**：否。`DeleteNodeAsset` 是 admin 单事务，只做 DB 软删 + 依赖表硬删（`DELETE FROM t_proxy_outlet WHERE node_id=?`），**不碰两台中转的 config.yaml、不停落地服务**。但高度相关：删除时这三个出口早已被改绑到别的 node_id（CA/US/NL/FR 11:31 绑 47.251.121.91、SG/JP 12:21 绑 45.32.20.165），`DELETE ... WHERE node_id=被删机器` 命中 0 行 → 三个坏出口幸存且仍 `listed` → 白名单裁剪仍全量下发。

**配置核对（不 OK 之处）**：`t_proxy_outlet.node_id` 只是台账归属，不驱动路由；真正决定链路的是中转 config.yaml 的端口映射。现有 3 处错位：SG(26019)绑 45.32.20.165 实际走 139.180.130.194；NL(26023)绑 47.251.121.91 实际走 78.141.208.60；FR(26024)绑 47.251.121.91 实际走 139.180.130.194。删掉这 3 行后剩余 JP/CA/US 的绑定反而与真实路由全部对齐。另：中转 hy2 `password: HY2_PASSWORD` 是字面占位符当真密码且 6 出口共用；urltest interval=86400 + lazy 使坏节点只标不可用、不自动从列表剔除（fallback 仍可用，不影响实际翻墙）；地域名与实际 IP 不符属人工维护项。

**GetLinks 真实调用验证（自签只读 access JWT，uid 取已有 credential 的用户避免写库）**：`code=0`、`has_subscription=true`、`selected_node_id=relay-47-120-10-73-01`；返回 23268 B vs 后端模板 22903 B，精确 diff **只有 12 行**：6 处 `server: RELAY_HOST→47.120.10.73` + 6 处 `password: ANYTLS_PASSWORD→v1.cr_...`（同一 HMAC 凭据），无占位符残留；6 出口 + 3 分组名完全一致、分组引用完整，白名单裁剪未删任何出口（6 全 listed）。上一轮 diff 看到的「尾部空行」是 `mysql -N -B` 采集附加换行造成的假象。**结论：前端/客户端拿到的内容与后端配置一致**，三个超时出口被原样下发正是现象来源。

**用户诉求：删除这两台落地机后，是否要删 26019/26023/26024 的绑定** → 建议删，但必须删「出口记录/上架状态」，不能只解绑：前端 `ProxyOutletsPage` 注释明确「未绑定归属但 listed 的出口仍会下发，只是不会被任何机器级联下架」，只把 node_id 置空超时照旧。当前前端无单出口删除/下架入口，`SetNodeListing` 的状态 SQL 是 `UPDATE ... LEFT JOIN t_proxy_outlet ON o.node_id=a.node_id ... WHERE a.node_id=?`（按机器级联全部出口），直接按机器下架会误伤同机的 JP(26020) 或 CA/US(26021/26022)。推荐顺序（**待用户下令，本轮未执行**）：① 三个出口置 delisted 或硬删 `t_proxy_outlet` 三行，客户端重拉 GetLinks 即消失；② 同步清 `t_admin_proxy_config` 模板里 3 段 proxies 定义 + 3 个分组引用，消除后台 `unmapped_proxy_names` 漂移提示并防止复活；③ 清两台中转 config.yaml 里 26019/26023/26024 的 hy2 outbound / IN-NAME / anytls listener 并 reload；④ 若日后恢复这些地区，用新落地机重新登记。
