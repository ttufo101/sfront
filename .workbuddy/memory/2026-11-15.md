## 追问「中转身份能否复用纳管时的证书/指纹」（只读核查，结论：不能复用，但诉求应换个方式满足）

**查清的四条信任关系（方向不同，别混）**：
1. **ed25519 纳管私钥**：`keypair/import.go` 加密存 `t_deploy_secret`，**全局一把**，各节点 authorized_keys 放同一公钥；`executor/ssh.go:30-48` 用它 `ssh.PublicKeys(signer)` 登录。方向 deployer→节点，证明「控制面」不证明「这台机器」。
2. **host_key_fingerprint**：`ConfirmBootstrap` 人工确认固化 `/etc/ssh/ssh_host_ed25519_key.pub` 的 SHA256；`executor/ssh.go:52-70` `HostKeyCallback` 比对 `got != want` 拒绝，锁定 `KeyAlgoED25519`。方向是**deployer 校验主机防 MITM**，且只是公开哈希（握手明文下发、回执里也带）。
3. **node-id + node-password**：mihomo `component/starland/manager.go:555` 发 JSON 信封 `com{node_id,node_password}` → gateway `gateway.go:340-341` 转 `xmd-node-id`/`xmd-node-password` → `dataplane.authenticateNode`(`dataplane.go:225-242`) `bcrypt.CompareHashAndPassword`。方向 mihomo→Gateway，**这才是心跳身份**，每台唯一。admin `CreateDataPlaneNode`(`admin.go:504-524`) `newDataPlaneNodePassword()` 生成 32B 随机、只回显一次、bcrypt 入库。
4. **ANYTLS_PASSWORD**：GetLinks 下发的 HMAC，用户→中继接入凭据，与心跳无关。

**不能直接复用的 3 条硬理由**：① 指纹是公开可枚举值，当 `node-password` 塞进 `com`（gateway 只校验长度 ≤256）等于无鉴权，比 32B 随机密码倒退；② 方向反了，要用 host key 做认证必须让 mihomo 拿 `/etc/ssh/ssh_host_ed25519_key` **私钥签名** + Gateway 验签，那是新建 challenge-response/mTLS，且 host key 私钥 0600 root、mihomo 独立进程读不到，给权限/复制私钥又变成第二份静态密钥；③ 复用共用纳管私钥更糟——无法区分 node_id（分配/心跳/用量/审计全靠它），且中继在边缘，一旦攻破控制面私钥泄露 = 所有节点反向失守（现为单向）。

**改动面**：改证书认证要同时动 mihomo fork、gateway、dataplane、admin 注册表、台账 5 个组件 + 两台在线中继切换，为解「首装没段」这个 20 行闸门的问题不划算。

**满足真实诉求（别维护第二套静态密码）的最小路径**：把身份段**写入**归位到纳管流程，而非让发布中心签发——`CreateDataPlaneNode` 仍是唯一签发点（生成明文+bcrypt 入库），`ConfirmBootstrap` 之后用**已有 ed25519 SSH 通道**把 3 行写进目标机 `/opt/mihomo/conf/config.yaml`(0600)，与注册同流程完成；发布中心仍只做「提取保留 + 缺失即拒绝」。零协议改动、消除人工复制、首装必然有段，与上一轮方案 3 完全兼容（「发布中心不签发」指发布中心，纳管流程签发是职责归位，二者不矛盾）。代价：admin 需 SSH 写权限或复用 deployer 通道、需处理写入成功但服务未重启的状态。

**P2/P3 正解（现在不做）**：控制面 CA 给每台中继签客户端证书，mTLS 握手取 node_id，可同时做到每台唯一/无明文密码/可撤销轮换；但要引入 CA 生命周期、改 5 个组件、切换在线中继。当前仅 2 台，收益不抵成本。

**状态**：纯只读核查，未改代码/配置/数据。

## 再追问「裸机纳管最早发生，mihomo 能否读 host key 指纹做身份识别、两处一致」（结论：指纹只能做名字，不能做凭证）

**用户纠正成立的时序**：纳管时是裸机，无 mihomo、无 `/opt/mihomo/conf/config.yaml` → 上一轮提的「ConfirmBootstrap 之后写 config.yaml」不成立，必须改为写**纳管态文件** `/etc/starland/node-identity`(0600 root)，装 mihomo 时由安装脚本读它生成 config.yaml 身份段；发布中心只读 + 保留 + 缺失即拒绝。这样首装必然有身份，且发布中心不签发、人工不搬运。

**纠正上一轮两处事实（只读实证）**：
1. **mihomo 本来就是 root**（`ps -eo user,...` → `root 3074428 /opt/mihomo/mihomo -d /opt/mihomo/conf`），host key 私钥 `-rw------- 1 root root /etc/ssh/ssh_host_ed25519_key` → 「mihomo 读不到私钥」**不成立**，权限不是障碍。unit 是 transient（`/run/systemd/transient/starland-mihomo.service`，`Restart=no`），顺带注意发布中心 `systemd:starland-mihomo` 重启语义。
2. `GetBootstrapCommand` 回执只采 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub | awk '{print $2}'` 即 `SHA256:...` 指纹，**不含公钥全文**；`t_node_asset.host_key_fingerprint varchar(256)` 表注释明确「零凭据列」。要验签需新增公钥全文列 + 改回执。

**字面方案不可行的根因（identifier ≠ authenticator）**：指纹是公开可枚举值（SSH 握手明文下发 host pubkey、回执也回显），任何能连 22 端口者 `ssh-keyscan` 即得。「Gateway 比对登记指纹」与「把指纹当密码」在攻击者视角等价——**只需知道、不需持有**；换成等值比对还丢掉 bcrypt 慢哈希。后果是真实业务风险：`authenticateNode`(`dataplane.go:225-242`) 放行后 `ReportUsage` → `store.ApplyUsage` 直接写 `AccountedBytes`/`RemainingTrafficBytes`（流量记账/限流），并可伪造心跳标 online 影响 `ListHealthyRelayNodes` 分配。伪造门槛从「偷 32B 随机密码」降到「扫一次端口」。

**正确变体（技术上可行但要权衡）**：让 mihomo 用 host key **私钥签名**（challenge-response：Gateway 下发 nonce → mihomo 签 nonce+timestamp+body → Gateway 用登记公钥验签并映射 node_id），可真正取消第二套静态密码、无需 CA、密钥系统自带。改动面：纳管回执带 pub key 全文 + 台账加 `host_public_key` 列、mihomo fork、gateway `com` 字段、dataplane 鉴权、admin 注册表（`password_hash` 退役）、两台在线中继切换；必须带 nonce/时间戳防重放。**新增风险**：mihomo 是面向公网流量的 root 代理，让它持有 SSH 主机私钥 = 一钥两用，一旦 RCE 拿到的是机器根身份密钥（可对 SSH 客户端 MITM）；现在两份凭据其实是**故障域隔离**（node-password 泄露只影响数据面，不影响 SSH 主机信任），不是冗余。

**推荐平衡（简单务实）**：只统一**标识符**、不统一**鉴别材料**——`node-id` 用 host key 指纹（或稳定短哈希），纳管时自动固化，两处天然一致，顺带消掉 #38「显式确认 dataplane_node_id」的人工对齐；`node-password` 仍由 `CreateDataPlaneNode` 随机生成 + bcrypt 入库。零协议改动、零 CA、零在线切换。

**结论**：指纹能做「名字」，不能做「凭证」；要连凭证都省掉得上签名/mTLS（5 组件 + 在线切换 + 暴露面扩大），当前 2 台中继不划算，留 P2/P3。

**状态**：纯只读核查，未改代码/配置/数据。

**结论（只保留脚本 = 正确，但要澄清层级）**：脚本是**操作接口**、systemd 是**托管机制**，不是二选一；发布中心只调 `script:/opt/<app>/setup.sh`，底层由脚本用 systemd 托管。收益：删 systemd 分支与 unit 名映射、消掉 #48「落地机无 unit 导致部署失败」、健康检查复用同一脚本 `status`、前端枚举 5 项收敛到 1 项。**必须同步修模板两点**：① 支持启动参数（mihomo `-d conf`、hysteria `server -c conf/config.yaml`），用 `$SERVICE_DIR/conf/start-args` 可选文件，消除改脚本副本的差异化；② transient + `Restart=no` 改常驻 unit + `Restart=on-failure` + `RestartSec` + `StartLimitBurst` 限流（fail-closed 时避免无限重启刷屏，也不能静默离线）。接口不变、只改内部，已运行的 10 个服务不重启不受影响，可灰度。

**统一约定**：`/opt/<app>/{<app>, conf/config.yaml(0644 零凭据), conf/start-args, setup.sh(0755 同一份), log/, <app>.pid}`；`/etc/systemd/system/starland-<app>.service` 常驻；`/etc/starland/node-identity`(0600 root) 跨应用、不属于任何应用目录。`<app>` 由 `service_type` 白名单推导（relay→mihomo、landing→hysteria）。

**应用定义契约收敛**：前端不再提交任何路径/命令，后端推导 `config_target_path=/opt/<app>/conf/config.yaml`、`bin_target_path=/opt/<app>`、`restart_cmd=health_check=script:/opt/<app>/setup.sh`；`start_cmd/stop_cmd/identity_path` → proto reserved；`CreateAppDefinitionRequest` 只剩 `app_key/display_name/service_type`（+可选 config_filename），表单 8 项→3 项。沿用 `reserved 7` 已验证的后端推导手法。代价：失去自定义路径能力，P0 两种服务下值得。

**端到端执行逻辑**：纳管（裸机：bootstrap 回执 → 确认 host key 指纹 → `CreateDataPlaneNode` 生成 32B 密码+bcrypt 入库 → SSH 写 `/etc/starland/node-identity`，含 node_id=指纹 / node_password / gateway_url 按机实际）→ 首次安装（统一流程：解压到 `/opt/<app>`、写纯净模板、装统一 setup.sh+unit+start-args、`setup.sh restart`；mihomo 启动自读身份，fail-closed；安装流程对所有 service_type 完全相同）→ 升级/回滚（同一路径：写模板→解压→restart→status，无 first_install / 无 identity / 无 service_type 分流）→ 失败不自动回滚，台账如实记。身份轮换/重装：改身份文件 → restart；缺失 → 拒绝启动 + 发布中心前置提示先纳管。
