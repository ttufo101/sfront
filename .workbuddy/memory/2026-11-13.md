## 分析：数据面中转节点「在线状态」维护机制（未改代码）

结论：`runtime_status` 是 `t_dataplane_node` 的持久化字段，非实时探测；admin 列表纯 SELECT。

链路与源码依据（develop-hy `/root/sproj`）：
- `mihomo/component/starland/manager.go:169-205` `lifecycleLoop`：启动发 `NodeOnline`（失败每 5s 重试，未上线不发心跳）；成功后每 `heartbeat-interval-seconds` 发 `Heartbeat`，默认 15s（`:140-145`）；正常退出 `NodeOffline(graceful_shutdown)`，配置 reload 用 `configuration_reload`。`boot_id` 为进程启动随机 16 字节 hex。
- 两台机 `/opt/mihomo/conf/config.yaml` 的 `starland-dataplane` 段都未显式设 heartbeat-interval → 15s。develop-hy `relay-47-120-10-73-01` → `127.0.0.1:12001`；develop-tg `relay-106-52-77-108-01` → `47.120.10.73:12001`。

- `apps/dataplane/internal/service/dataplane.go:220-243` `authenticateNode`：查表 + bcrypt 比对 `password_hash` + 检查 `enabled`，通过后 `TouchNode` 刷 `last_seen_at`（任意节点 API 调用都会刷，故 `heartbeat_at` 才是心跳依据）。
- `apps/dataplane/internal/data/data.go:98-150` 三条 UPDATE：`MarkNodeOnline`（置 online 并清 offline_at/offline_reason）、`HeartbeatNode`（WHERE 仅 node_id+boot_id，RowsAffected=0 → 409 stale）、`MarkNodeOffline`。

## 发现的三处缺陷（未修，待用户决定）
1. **心跳复活不清离线残留**：`HeartbeatNode` 的 SET 缺 `offline_at=NULL, offline_reason=''`，WHERE 也不带 runtime_status 条件，故 offline 节点靠心跳可直接复活但残留旧离线信息。实测两节点 online 却仍带 11-11 17:38:36 `heartbeat_timeout`；前端仅在 `runtime_status==='offline'` 时展示离线信息，把残留藏住了。最小修复：在 HeartbeatNode 的 SET 补两列（与 MarkNodeOnline 对齐）。
2. **阈值双口径**：后端 45s 判 offline，前端 `isAssignable` 用 300s 判断心跳有效。正常路径下前端阈值冗余（后端先拦），真正价值是 dataplane 整体挂掉/sweep 停摆时兜底「可分配」，但「运行状态」列仍会冻结显示在线，有误导。日志佐证 11-11 17:35~17:38 sweep 连续 `context deadline exceeded` 失败。
3. **stale boot id 无自愈**（代码路径推断）：Heartbeat 返回 409 时 `lifecycleLoop` 只打日志、不把 `online` 置回 false，因此不会重发 `NodeOnline`；若 DB 中 boot_id 与运行进程不一致（手工改库/DB 恢复），节点会一直 409 且永不重新上线，需重启 Mihomo。最小修复：收到 stale 时重置 `online=false`。
