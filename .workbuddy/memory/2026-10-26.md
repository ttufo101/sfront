## 反馈诊断日志下载修复（已构建部署）
- **根因**：`FeedbackPage` 用 `getAppReleaseDownloadUrl(file_id)`（安装包接口 `/api/v1/app-releases/{id}`，直连 MinIO 匿名读）下载诊断日志；但诊断日志实际走 `log-files` 资源（fileupload `ObjectPrefix:"logs"`、`ResourcePath:"/api/v1/log-files"`），存 MinIO `logs/` 前缀，不在 `app-releases/`，故 404。

- **修复**：`fileApi.ts` 新增 `getDiagnosticLogDownloadUrl`（→ `/api/v1/log-files/{id}`，沿用 fileApiBase）；`FeedbackPage` 改为 `fetch(url,{Authorization:Bearer})+blob+<a download>` 本地下载，含下载中状态与错误 toast。
- 构建部署同上；线上 bundle 含 `log-files`/`已开始下载`/`下载中` 串，443/深路由 200。

## 反馈下载 "Failed to fetch" 二次修复（已部署）
- **现象**：上一轮把 window.open 改成 `fetch+Authorization+blob` 后，点击"下载日志"仍报 `Failed to fetch`（网络层失败，非 HTTP 4xx）。
- **根因定位（实测）**：openresty 的 `/api/v1/log-files/` location **原无 CORS 头**；而 `/api/v1/app-releases`（上传走此）本就有 CORS 头。解释"上传能用、下载报错"的不对称——**后台页面若以 HTTP 访问（origin=`http://106.52.77.108`），而 `VITE_FILE_API_BASE` 写死 `https://106.52.77.108`，则文件请求跨域**：app-releases 有 CORS 放行、log-files 无 → 下载预检失败 → Failed to fetch。
- **修复两处**：
  1. **前端 `.env`**：`VITE_FILE_API_BASE=` **置空** → 文件请求走**相对路径**，跟随页面自身 origin，`resolveFileUrl` 不再拼绝对 https。无论页面以 http/https/域名访问都不再跨域、不再混合内容。这是根因修复（已 rebuild+deploy，线上 bundle 已无硬编码 106.52.77.108）。
  2. **openresty nginx.conf `log-files` 块**：补 CORS（`if ($request_method=OPTIONS){...return 204}` + `Access-Control-Allow-Origin $http_origin` + expose headers）；并把 `limit_except GET HEAD {deny all}` 改为 `limit_except GET HEAD OPTIONS {deny all}`（原 limit_except 在 nginx 里与 if return 204 冲突，会把 OPTIONS 拒成 403）。双保险。
  3. **前端错误提示**：`FeedbackPage` 下载 catch 区分 `TypeError`（网络/证书未信任）给出可操作提示（确认已信任 106.52.77.108 自签证书 / 看控制台 net::ERR_CERT·CORS）。
- **验证**：nginx `-t` 通过、reload 成功；443 OPTIONS 预检实测 `204 + CORS 头`、GET `401 + CORS 头`；443/80 深路由 200；清理上版孤儿 `index-YQX8db78.js`。
- **部署坑复盘**：之前一度 `!~ ^(GET|HEAD|OPTIONS)$` 因未加引号 heredoc 被 bash 把 `$request_method`/`$)` 当变量插值吃掉，写坏配置导致 reload 失败（窗口期内 443 仍 403）。教训：改 nginx 用本地写脚本文件 scp 执行、勿用未引号 heredoc。
